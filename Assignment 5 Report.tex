\section{Program summary}
This program is based around a \verb|Lepton| class, which is an abstract base class from which \verb|Electron|, \verb|Muon|, \verb|Tau|, and \verb|Neutrino| are derived classes. The \verb|Lepton| class contains a unique pointer to a \verb|FourMomentum| object, whose class has energy, x momentum, y momentum, z momentum, and rest mass, as data members (all measured in MeV). The \verb|Lepton| class also contains a rest mass and relative charge, as well as a boolean expression which if true represents an antilepton by flipping the charge data member. The \verb|Lepton| class contains 2 virtual member functions which makes it abstract (along with its virtual destructor). The first is the \verb|info()| function which is used to print out additional properties of derived classes, and \verb|has_decayed()| which is set true if one of the derived leptons have decayed. \verb|Lepton| contains \verb|base_info()| to print out the properties it carries (four momentum, rest mass, and relative charge).

The derived classes inheret all these properties, but also have their own data members and member functions. These additional properties are printed by overriding the \verb|info()| function (using \verb|base_info()| to print the properties from \verb|Lepton|), and are used to determine the outcome of \verb|has_decayed()|. Figure \ref{fig:UML} is a UML diagram which shows the heirarcy of the derived classes, and their properties. All of the derived classes use \verb|static constexpr| to store their mass and charge as constants which cannot be modified during compilation or run time, which are printed via \verb|base_info()|.

The lepton class also contains 2 friend functions - one to sum the four momenta of 2 leptons, and the other to compute their dot product.

\subsection{Electron class}
This class introduces an interaction with a detector, primarily through calculating the shower depth in a tungsten (W) detector via the member function  \verb|shower_depth_in| \verb|_tungsten()|. This function calculates the shower depth $X$ using the equation

\begin{equation} \label{eq:shower_depth}
	X = X_0 \frac{ln(E_0/E_c)}{ln2},
 \end{equation}

where $X_0$ is the radiation length, $E_c$ is the critical energy, and $E_0$ is the initial energy of the electron (from its \verb|FourMomentum|). The first two of these are set within the member function, matching the values for tungsten. $E_0$ is accessed via the pointer to the \verb|FourMomentum| from the Lepton base class. \verb|Electron| also has the function \verb|shower_contained(const double detector_length_in)| which, given a detector length, determines if the shower is contained within the detector.

\subsection{Muon class}
The \verb|Muon| class introduces the data member \verb|time_in_detector()| which, if greater than the constant \verb|MUON_MEAN_LIFETIME| stored as a private data member in the class, sets \verb|has_decayed()| to be true. A \verb|validate_time()| static function is used to check that the time entered by the user is not negative or greater than 1 second.

\subsection{Tau class}
The \verb|Tau| class  uses \verb|time_in_detector()| and with \verb|TAU_MEAN_LIFETIME| to handle the \verb|has_decayed()| function, akin to the \verb|Muon| class. Unlike the \verb|Muon| class, however, it takes into account the different decay modes of taus. Using the fact that 64$\%$ of the time a taus' decay products are hadronic, 17.8$\%$ of the time they involve electrons, and 17.4$\%$ of the time they involve muons, a private member function \verb|generate_decay_mode()| uses a basic Monte Carlo simulation to set the \verb|decay_mode| data member to one of the three named values in the enumerator class defined for the decay modes. The getter \verb|get_decay_mode| uses a switch to return the decay products as a string, differing for each named value in the enumerator class, and this is used in the overriden \verb|info()| function.

\subsection{Neutrino class}
In the neutrino class, the idea of lifetime is discarded and \verb|has_decayed| is always set to false due to the stability of neutrinos. An enumerator class \verb|NeutrinoFlavour| is used with three named values corresponding to the three neutrino flavours. The neutrino flavour is set as a private data member which can be specified via the neutrino constructor or flavour setter. Since a neutrino cannot be flavourless, the default constructor also requires flavour as an input. The \verb|info()| function prints the flavour using a switch returning a string dependent on the named value in the enumerator class, as well as the flavour generation, again dependent on the named value.

\subsection{Main cpp file}
The main file is split into 6 parts. The first part creates a vector of different leptons called \verb|particles| via unique pointers to the base \verb|Lepton| class, and then prints out all of their info using an iterator through all elements in the vector. The second part accesses 2 electrons by dereferencing the first two elements and sums their four momenta. The third part accesses the anti electron and anti muon and takes the dot product of  their four momenta. The fourth part creates a unique pointer to an electron and moves it to a second pointer. The fifth part creates a shared pointer for a tau lepton and assigns into to 2 other pointers. The final part creates 2 vectors of shared particles ("detectors"), and gives them the same tau lepton pointer, which is shown by printing out all elements in both of the vectors.

\section{Code design}
\subsection{Four momentum class}
The \verb|FourMomentum| class was changed so that, unlike in assignment 4 where its only data member was a unique pointer to a 4-vector containing energy E and the 3-momentum components (px, py, pz), it contained each component as a separate data member. This made the object easier to deal with when performing checks for invariant mass, since it relates to the four momentum components via the equation

\begin{equation} \label{eq:fm}
	m^2  = E^2 - \mathbf{p}^2,
 \end{equation}

where $m$ is the particle's rest mass (also known as invariant mass) and $\mathbf{p}$ is the 3-momentum. 

The desire to include invariant mass originates from distinguishing different derived classes of \verb|Lepton| with the particle mass, and therefore any \verb|FourMomentum| object which the derived classes deal with must give an invariant mass which matches the rest mass of that specific particle. The issue with \verb|FourMomentum| class as in assignment 4 was that it required the user to specify E, px, py, pz in one go to generate the 4-vector. This was resolved by making the FourMomentum class have E, px, py, pz as data members themselves, allowing the 3-momentum to be set by the user, and then using the invariant mass equation to determine the energy and define the FourMomentum object.

Setters for E, px, py, pz would allow the user to modify the \verb|FourMomentum| object and change the invariant mass, completely breaking checks for invariant mass. This was first resolved by removing all setters from the \verb|FourMomentum| class, and only allowing (px, py, pz) to be set via the \verb|Lepton| base class (through its constructors). Since \verb|Lepton| contained a mass data member, the energy could then be computed using equation \ref{eq:fm}, creating a valid \verb|FourMomentum| object. Individual setters for px, py, pz were then possible by re-computing the energy.

This however made the \verb|FourMomentum| object completely redundant, as it was mostly controlled by the \verb|Lepton| class, and the user could make a \verb|FourMomentum| object which completely broke these checks. To avoid this, the code was redesigned to keep the control of the \verb|FourMomentum| object completely within the \verb|FourMomentum| class, thus disallowing a \verb|FourMomentum| object to be created which didn't obey equation \ref{eq:fm}. One idea was to make \verb|Lepton| a friend class of \verb|FourMomentum| and making the constructors private such that a \verb|FourMomentum| object could not be created outside of that class. This didn't work, however, due to the unique pointer in the \verb|Lepton| class, as it makes a new FourMomentum object not associated with the Lepton class, which wouldn't be possible.

The solution used was to redesign the \verb|FourMomentum| class to also include a mass as a data member which could be used to perform check. The \verb|Lepton| class can then pass its mass into the constructor of the form (m, px, py, pz). This is more robust, as if the user wanted to make another base class, e.g. quarks, using \verb|FourMomentum|, they wouldn't need to worry about checking that invariant mass is conserved, as all checks would be handled by the \verb|FourMomentum| class. One issue that came up was with the friend function which summed the four momenta of 2 leptons, as this required a constructor in \verb|FourMomentum| of the form (E, px, py, pz), which could not be overloaded as it contained the same elements of the same type as the (m, px, py, pz) constructor.

To get around this, a constructor of the form (E, px, py, pz, m) was made private, and two static functions \verb|four_momentum_from_mass| and \verb|four_momentum_from_energy| were introduced, where the latter allowed for the four momenta sum to be computed. This also gave the benefit that a user, who may not know the mass of a particle but does know its initial energy, could find its invariant mass and still construct a \verb|FourMomentum| object (this is technically what is done when 2 four momenta are summed - a new combined invariant mass is calculated so that the new summed \verb|FourMomentum| object still obeys equation \ref{eq:fm}). Setters for px, py, pz were added in the \verb|FourMomentum| class, which assumed the invariant mass was conserved (and energy changed) to keep in line with requirements for the \verb|Lepton| class. Setters for mass and energy were not possible as both would allow the user to modify the rest mass.

The overload \verb|<<| operator ensures that only E, px, py, pz are printed out when a \verb|FourMomentum| object is called - the rest mass can be thought of as a "hidden" property.

\subsection{Lepton class}
In the main function for this assignment, we are never required to deal with just a lepton, but rather some specific type of lepton. Also, there is no need to work with lepton object - anything that is a lepton has a more specific particle category (e.g. electron, muon) with defined properties. Making \verb|Lepton| an abstract class therefore makes most sense. To make \verb|Lepton| an abstract class, at least one virtual function needs to be pure virtual. To adhere to this required making the \verb|info()| function print only additional features which \verb|Lepton| doesn't have, this allowing the info function to be pure virtual. To avoid repeating code, the \verb|base_info()| function was added to print out features which \verb|Lepton| does have, which can then be reused in all derived classes.

\verb|constexpr| was used for the mass and charge of all derived classes of \verb|Lepton|. It specifies that the mass and charge values of the derived object can be evaluated at compile-time, i.e. it doesn't change during run-time. It makes it obvious that mass and charge are physical constants and there are no changes of setting these incorrectly elsewhere in the program. The mass and charge were set to private data members, to keep it separate from the getters \verb|get_mass| and \verb|get_charge|, giving the user only one way to access them, consistent across all derived classes.

The other property of \verb|Lepton| is the four momentum. The lepton class uses a \textbf{unique} smart pointer called \verb|momentum_ptr|, which points to a four momentum object. It is a unique pointer rather than shared because \verb|FourMomentum| is a property which should be unique to a lepton. Shared pointers allow multiple pointers to point to the same object, so if the user wanted to change the \verb|FourMomentum| object of one lepton, it would also change it for all leptons which point to the same \verb|FourMomentum|. Also the FourMomentum of one object cannot be deleted until all shared pointers become out of scope, making it more difficult to deal with four momenta sums or dot products.

This assignment required moving the four momenta sum and dot product to be friend functions of \verb|Lepton| instead of \verb|FourMomentum|. It makes sense that these operators are not non-member functions, as this would require unecessary calling of the \verb|Lepton| class getters / setters. So that these functions can instead access the private data members of \verb|Lepton| class, i.e. the four momentum, these should be friend functions of Particle class. This makes more sense than having them as member functions of \verb|Letpon|, since being a member function would require one \verb|FourMomentum| to call another FourMomentum object with which it wishes to perform a sum or dotProduct operation. This would imply that the two FourMomentum objects are not equal in some ways.

To deal with antileptons without creating separate classes for them, a boolean parameter in the \verb|Lepton| base class \verb|is_antiparticle| was introduced, which is true if it is an antiparticle, and false if it is not. The charge is then set to be negative of the lepton's default charge (set via \verb|constexpre|) if its an antilepton. The user can never set the charge - the derived classes specify this, and setters for charge do not exist. If the user does not specify \verb|is_antiparticle| in the constructor, it defaults to false, i.e. assumes it's a lepton and not an antilepton. Default constructors for all derived classes assume the given particle is not anti. Note that \verb|is_antiparticle| must be set via the constructor so that if the user sets it to true this is matched when printing it out in the \verb|info()| function.


\subsection{Rule of 0/3/5}
The \verb|FourMomentum| object has the data members E, px, py, pz which are all doubles. As there are no pointers involved (or any other objects of non-class type), we use the rule of 0. As such, the \verb|FourMomentum| object does not need to have user-defined special member functions. Since the \verb|Lepton| class involves a smart pointer, we must implement the rule of 3 at least. As the assignment requires \verb|std::move| of \verb|Electron| (derived from \verb|Lepton|), we need move semantics and so must implement the rule of 5. All derived classes inherit the constructors and assignment operators defined in \verb|Lepton| base class, and since they do not have any pointers themselves, we use rule of 0 for derived classes.


\subsection{Class input validation}
All of the derived classes introduce private member functions which need to be specified via the constructors (or setters). These inputs must be checked so that they are physically correct. This is usually done via a static private member function starting with \verb|validate| which performs the checks and throws an invalid argument error, so that it can be reused in both constructors and setters within the class. The details of the validation checks for all classes in this program is shown below.
